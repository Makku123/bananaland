# Session 2026-06-20 1830 — Guaranteed-win Super Banana rune hint

Per the user: "when someone can afford the super banana, the super banana is revealed,
the person has a rune to land on the super banana and everyone has less than 3 runes,
give them a notification to use the rune that would make them win on their next turn."

## Implementation (frontend only)
`frontend/game-screen.js updateWinHint()` (called per-frame in showGame) toggles a
`#win-hint` banner (index.html + `.win-hint` CSS in styles.css). Shows it to the viewer
when ALL hold:
- `gs.state === "playing"`, viewer not bankrupt/ghost, holds ≥1 rune.
- **Every player has `rollCardCount < 3`** → no one can cast a Cancel (cancel needs ≥3),
  so the rune-play is uncancellable. (Literal reading of "everyone has less than 3 runes".)
- The Super Banana is in the viewer's `gs.boardLayout` (group `"superBanana"` → revealed to
  them) and **unowned**; viewer's `money >= sbPrice`.
- A held rune lands **exactly** on the SB (you must LAND to buy): `needed =
  (sbPos - me.position) mod boardLen` in 1..12; winning value = `needed>=7 ? 13-needed :
  needed` and `me.rollCards.includes(it)`. Negative-roll mode handled: needed 7..12 needs
  Negative ON; the banner adds "— turn ON/OFF Negative roll first" when the viewer's current
  mode is wrong.
- Wording: "Play your N Magic Rune **now**" (their turn, not yet rolled) or "**on your next
  turn**".

All data is client-available (rollCards owner-only, rollCardCount/boardLayout(revealed)/
money/position to the viewer) → no fog leak, no backend change.

## Verify
- Frontend harnesses 43 + 20; backend untouched (suite stays 1012/0); syntax clean; no
  console errors.
- **Live (DOM, screenshots wedged):** 10 stubbed scenarios — happy 5-step win (shows
  "Play your 5 …"); hidden when someone has ≥3 runes / can't afford / no winning rune / SB
  owned / target too far (needed>12); negative-mode needed=8 → "Play your 5 … turn ON
  Negative roll first" (and no note when already negative); "now" vs "next turn" wording.

## Known limitation (acceptable per the user's stated condition)
A Cancel cast on the viewer LAST turn by someone who has since dropped below 3 runes is
invisible to the client (`cancelQueued`/`cancelActive` are redacted server-side), so the
banner could over-promise in that rare pre-cast-then-spent-down case. The user defined the
trigger as "everyone has less than 3 runes," which this implements faithfully; fully closing
that edge would need a backend-assisted "am I cancelled?" flag.

## Adversarial review + fixes
8-agent review → **NO-GO as written**, fixed to GO:
- **HIGH (fixed):** the afford check used the SB tile's `boardLayout.price`, which is a
  STALE hardcoded **1600** (`board[sbPos].buyable.price`), not the configured
  `superBananaPrice` (default 4000, applied only to the properties-map copy). So a viewer
  holding 1600–3999 saw a false "WINNING MOVE." Fixed to read the real charged price from
  `_gsPropMap[sbPos].price` (falls back to `gs.superBananaPrice`). Verified: money 2000 vs
  real 4000 → hidden; also correct for sub-1600 prices.
- **LOW (fixed):** the no-cancel scan counted EVERY player — including bankrupt, ghosts, and
  teammates who can never cast a Cancel — so any of them holding ≥3 wrongly suppressed the
  banner. Fixed to only count LIVE, non-teammate opponents (excludes self too). Verified:
  ghost/bankrupt/teammate with 5 runes no longer suppress; a live enemy with 3 does.
- **MEDIUM (won't-fix, by design):** a Cancel pre-cast on a prior turn by someone now < 3
  runes is invisible to the client (`cancelQueued`/`cancelActive` are redacted), so the
  banner can rarely over-promise. The review suggested a backend owner-only `cancelPending`
  flag, but exposing that would **break the Cancel mechanic** (the target could dodge every
  cancel by simply not playing a rune). Left as a documented, rare, inherent-to-secret-
  cancels limitation; kept the confident wording the user asked for.
