# Session 2026-06-19 1558 — Pink/purple ownership borders + premature fog reveal (+ related audits)

Two reported bugs, each investigated for the broader class (parallel workflow + independent verification).

## Bug 1: pink/purple ownership borders don't show
- Root cause: board.js:915 adds class `owned-<ownerColor>` to owned tiles, but styles.css only defined `.owned-brown/.owned-golden/.owned-silver/.owned-red` — no `.owned-purple`/`.owned-pink` → those players' owned tiles got the default 1px border, not the 8px coloured border+glow. Same class of gap as the earlier `.pile-pink`/`.pile-purple` fix.
- **Related audit (exhaustive):** checked ALL per-player-colour CSS families that JS applies from `player.color` — `.owned-`, `.pile-`, `.c-` (monkey/avatar/pstat/owner/chart/lobby consumers), `.board-chat-dot/name/mention.c-`, `.lobby-player-avatar.c-`. **Only `.owned-` had a gap.** Every other family already covers all 6 colours. (The `.g-<color>` families are tile-GROUP names, not player colours — left alone.)
- Fix (styles.css): added `.owned-purple` (#9b59b6) and `.owned-pink` (#ff5fa2) base rules + `ownGlowPurple`/`ownGlowPink` keyframes, and added them to the shared 8px border-reset selector. **No `body.mode-standard` variant** — purple/pink are intentionally never re-skinned, so the base rule applies in both themes.
- Verified (computed styles): `owned-purple` → 8px rgb(155,89,182)+ownGlowPurple; `owned-pink` → 8px rgb(255,95,162)+ownGlowPink; a no-rule colour falls back to 1px default (what pink/purple used to do).

## Bug 2: tile reveals before the token lands ("sometimes")
- Root cause: the board fog freezes the destination during a walk by using a PRE-move snapshot `window._diceRollingRevealed` (= `window._prevRevealedTiles`, board.js:653). But `_prevRevealedTiles` was snapshotted **inside** the `!window._tokenWalking` guard (game-socket.js). On an OVERLAPPING/auto-roll (a `game_update` arriving while the previous walk still animates), the guard skipped the snapshot → `_prevRevealedTiles` went stale → the freeze installed a wrong/empty set → the destination (already in the live `me.revealedTiles` the server ships in the same update) un-fogged immediately. This is the **exact** overlap bug already fixed for the pile snapshot — but never ported to the revealed snapshot (the pile snapshot already sits outside the guard; the revealed one didn't).
- **Related cases checked:** all move types (rollDice, useRollCard normal+negative+cancel-HIT, debugMove, ghost auto-roll) funnel through the same freeze; start-pick teleport correctly skips it; `itemMoveThisTurn` is dead; no other `revealedTiles.add` site is a premature-reveal vector (they reveal the already-arrived/landing tile or reveal-to-all). So the single fix covers all paths.
- Fix (game-socket.js): moved the `_prevRevealedTiles = new Set(me.revealedTiles)` capture OUT of the `!_tokenWalking` guard into its own ALWAYS-runs block (right after the pile snapshot, before `gs = state` / the `_gsPlayerMap` rebuild so it reads the PRE-move map). Safe because the walk holds its own `new Set` copy in `_diceRollingRevealed`, so refreshing the snapshot can't corrupt an in-flight freeze (same invariant the pile snapshot relies on). Server fog redaction untouched (this is pure client render timing).
- Verified: added P6 structural regression check to `frontend/test_pile_persist.js` (mirrors the pile P4) asserting the revealed snapshot now sits OUTSIDE the guard and exactly one snapshot remains → **20 passed, 0 failed**; pile harness still **43 passed**; `node --check` clean; CRLF preserved.

No backend changes. Workflow investigation confirmed both root causes and that no other related gaps exist.
